# MySQL 基础

## 第1章 选型

**本章路线：** 1.1～1.3 SQL/NoSQL 与适用场景 → 1.4 定 MySQL → 1.5 练习。

### 1.1 SQL vs NoSQL ★★★

|     | **SQL（关系型）**         | **NoSQL（非关系型）**              |
| --- | -------------------- | ---------------------------- |
| 含义  | 用 **SQL** 操作         | **Not Only SQL**（不是「不要 SQL」） |
| 形态  | 库 → 表 → 行/列          | 文档 / 键值等，模型多样                |
| 常见  | **MySQL**、PostgreSQL | MongoDB、**Redis**            |
| 访问  | 标准 **SQL**           | 各自 API，不统一 SQL               |

- 强关系、要事务 → 业务核心用 **MySQL**。  
- 缓存 / Token → **Redis**，与 MySQL **分工**，不是替换。

### 1.2 关系型：特点与适用 ★★★

| 特点       | 一句话                       |
| -------- | ------------------------- |
| **结构化**  | 存之前先定表结构；标准二维表（行/列、同列同类型） |
| **ACID** | 事务要么全成功要么全回滚，保证数据可靠       |
| **SQL**  | 查询、合并、聚合、多表关联             |

**ACID 四字（先记名）：** 原子性、一致性、隔离性、持久性。转账/扣库存不能执行一半。

部分新版本支持 **JSON 列**存半结构化数据，但主体仍是表结构思维。

**什么时候适合：** 实体之间有关系，且要**严格保证数据正确**。

| 关系例子           | 说明                  |
| -------------- | ------------------- |
| 订单 ↔ 订单明细 ↔ 商品 | 一件商品可进多笔订单，一笔订单多行明细 |
| 用户 ↔ 笔记        | 一人多篇笔记，一篇笔记只属于一人    |

要做统计、报表、复杂查询 → **SQL + 关系型**更合适。NoSQL 对事务/一致性支持通常较弱。

### 1.3 非关系型：特点与适用 ★★★

| 特点 | 一句话 |
|------|--------|
| **灵活模型** | 不必先定死表结构；同集合里各行字段可不同（如文档库） |
| **弱化 ACID** | 常换更高读写吞吐；难做银行级强事务 |
| **非统一 SQL** | Mongo 用文档 API；Redis 用键值命令 |

**典型场景（课内）：**

- **日志 / 埋点**：写入量大；一致性要求不严，偶丢几条可接受  
- **结构多变**：商品属性各异（颜色、口味等）→ 文档库（如 MongoDB）  
- **高并发轨迹**：用户行为流等，关系型难扛写入时  

**常见补充：**

- **缓存 / 会话 / 简单 KV**：→ **Redis**  
- **排行榜 / 计数**：Redis 原子增减等  

注意：通常更占空间；**不能替代**订单、支付等要强一致、强关联的核心库。多数业务仍以关系型为主库，NoSQL 作补充。

> 补：课内实战项目因「实体有关系 + 要事务」选定关系型；本仓库同样是 MySQL 核心 + Redis 缓存分工。

### 1.4 选型步骤与定 MySQL ★★★

关系型里还要再选具体产品（Oracle / MySQL / SQL Server …）。课内按 **五步** 筛，再落到 **MySQL**。

| 步骤 | 看什么 |
|------|--------|
| **生态与普及** | 用的人多不多？资料、招人、社区容不容易 |
| **成熟度** | 用得久、够稳定，才敢上生产 |
| **扩展性** | 数据量上来能否主从、读写分离、分库分表（中间件先认名） |
| **安全与稳定** | 加密、权限、备份恢复是否满足要求 |
| **成本与部署** | 授权费；是否支持你的 OS（Linux / Windows） |

原则：**合适比喜欢更重要**；不必盲目追「市场占有率第一」。

**定 MySQL 的常见理由（课内四块）：**

| 维度 | 要点 |
|------|------|
| **扩展** | 主从复制、读写分离；一实例多库；库/表级复制；MyCat / MaxScale 等中间件做分库分表（细节后学） |
| **安全** | SSL 传输加密；库/表/行级权限；备份恢复 |
| **高可用** | 主从集群；配合 **MHA** 等做故障切换（课内提 99% 可用目标） |
| **成本** | **开源免费**；社区版功能已够多数项目；Linux / Windows 均支持 |

- 排行榜前列多为关系型；**MongoDB** 是非关系型里较常见的一种  
- Oracle / SQL Server 偏商业授权；**预算有限** → 常选 **MySQL**  
- 运维、开发人才多 → 招聘与排障成本相对低  

> 补：PostgreSQL 也开源；课内与 Java 生态结合以 **MySQL** 为主线。

## 第2章 表设计

**本章路线：** 2.1 流程 → 2.2～2.5 逻辑（宽表 / 范式 / 建模 / 反范式）→ 2.6～2.9 物理（引擎 / 类型 / 选型 / 命名）。

### 2.1 表设计流程 ★★★★

定好 MySQL 之后，建库建表前要先做**结构设计**。课内分两大块（origin **3-1**）：

1. **逻辑设计** — 业务 → 实体/属性/关系 → 怎么拆表（2.2～2.5）  
2. **物理设计** — 引擎、字段类型、命名（2.6～2.9）；真正 `CREATE` 前再定  

**逻辑设计三步（建表前）：**

| 步骤 | 干什么 | 产出 |
|------|--------|------|
| **业务分析** | 从业务页面/流程找：存什么、谁和谁有关 | 实体清单 + 属性清单 + 关系（常见 **1:N**） |
| **逻辑设计** | 宽表/范式、拆表、字典与 FK | ER / 表结构草案（仍不写具体 SQL 类型） |
| **物理设计** | 引擎、类型、命名 | 可执行的 DDL 方案 |

**业务分析怎么做（origin 3-2～3-3）：**

- 按**功能模块**过一遍：列表页、详情页、用户中心…  
- 每个模块问：**有哪些对象？每个对象有哪些描述信息？**  
- 对象 → **实体**（用户、订单、商品…）；描述信息 → **属性**（昵称、价格、发布时间…）  
- 标关系：一门课多个章节 → **1:N**；一个用户多条评价 → **1:N**  
- **此步只清单，不写 SQL、不定 varchar 长度**  

**常见实体类型（认名）：**

| 类型 | 例子 |
|------|------|
| 主数据 | 用户、商品、课程 |
| 明细 / 子项 | 订单明细、章节、小节 |
| 业务记录 | 评价、问答、笔记 |
| 字典 | 分类、难度、状态码 |

逻辑设计好坏 → 直接影响以后**扩容、查询效率、好不好改**。

先逻辑后物理。落库：`CREATE DATABASE` / `CREATE TABLE`（第 3 章 SQL）。

### 2.2 宽表 ★★★★

**宽表**：把多个实体/字典的信息**挤进一张表**，同一信息在**多行重复**（如每行订单都冗余存「客户姓名、客户地址」）。

**三大异常（origin 3-5～3-7，课内纠错）：**

| 异常 | 含义 | 典型后果 |
|------|------|----------|
| **更新** | 改一处本应改全库，却只更新了部分行 | 同 teacher 多门课，只改一行 → 其它行职位仍旧，**数据不一致** |
| **插入** | 缺「主数据」就插不进；或字典绑死在业务表里 | 新分类已维护，业务表无对应行 → 前端下拉**空项**；字典无法单独维护 |
| **删除** | 删业务行顺带删掉字典/主数据 | 删一条业务记录 → 分类下拉少一项，**误伤公共数据** |

- **不是绝对错误**：读多写少、**报表/统计**、要少 JOIN 时，宽表/冗余**可以用**  
- **OLTP 在线业务**（订单、用户、库存）：**宜拆表** — 主数据单表 + 字典表 + **`xxx_id` 外键**  
- 拆法方向：重复信息 → 独立表；业务表只存 id  

> 补：宽表问题本质是**冗余**；后面范式（2.3）从规则上消除冗余。

### 2.2 练习 ★★★★

#### 口述题

1. 什么叫宽表？  
2. 更新异常举一个业务例子。  
3. 插入异常举一个业务例子。  
4. 删除异常举一个业务例子。  
5. OLTP 为什么一般不用宽表？宽表适合什么场景？  

#### 答案

1. 多实体信息挤一张表，同一数据多行重复。  
2. 改客户地址只改一行订单，其它订单地址仍是旧的。  
3. 字典绑在业务表里，新字典项无法单独存在，或下拉缺项。  
4. 删订单顺带把分类/地区等字典删掉。  
5. OLTP 写入多，三大异常代价大；报表读多写少、少 JOIN 时可用。  

#### 判断练习

下面更像宽表问题还是拆表合理：**A** 订单表每行存 `customer_name` · **B** 订单表只存 `customer_id` 查用户表 · **C** 日报宽表一次查全字段少 JOIN  

#### 判断答案

A 宽表冗余 · B 拆表合理 · C 宽表/反范式在报表场景可接受  

### 2.3 三大范式 ★★★★★

课内**逻辑设计规则**（origin **3-8～3-10**）：OLTP 表至少满足 **3NF**；满足前序才能谈后序，**不可跳级**。

口诀：**1NF 管原子，2NF 管完全依赖，3NF 管传递依赖**。

| 范式 | 要求 | 违规 → 改法 |
|------|------|-------------|
| **1NF** | 字段**不可再分**（原子） | 「手机/座机/邮箱」拼一列 → 拆成多列 |
| **2NF** | 在 1NF 上；非主键**完全依赖整个主键** | 复合主键 `(user_id, chapter_id, title)` 里存「用户昵称」（只跟 user 有关）→ 拆 **user 表** |
| **3NF** | 在 2NF 上；非主键**只依赖主键**，不依赖其它非主键 | 课程表存「分类名、难度」（跟 `category_id` 走）或「讲师职位」（跟讲师走）→ 拆 **字典表 / 讲师表** |

**怎么判断（课内方法）：**

1. **1NF**：还有没有「一格多义、可再拆」的列？  
2. **2NF**：主键是**一列**还是**多列组合**？非主键列是否**只跟主键的一部分**有关？  
3. **3NF**：非主键列之间有没有**传递依赖**（A→B→C，C 不该留在本表）？  

**通法：** 违规列 → **独立表 + 外键 id**；业务 OLTP 目标 **≥ 3NF**；报表层可反范式（2.5）。

> 补：范式多，日常设计**前三范式够用**；BCNF 等后学。

### 2.3 练习 ★★★★★

#### 口述题

1. 1NF / 2NF / 3NF 各管什么？  
2. 联系方式「手机/座机/邮箱」拼一列，违反哪条？

### 2.4 逻辑建模 ★★★★

范式定完后，把 **2.1 业务分析** 的实体**落成表结构**（仍不写具体 SQL 类型）。课内方法（origin **3-11～3-16** 归纳，用通用说法）：

**逐实体过一遍：这列放哪张表？**

| 原则 | 做法 |
|------|------|
| **一实体一表** | 用户、商品、订单、课程等各一张主表 |
| **字典独立** | 分类、难度、方向、状态 → **字典表**，业务表只存 **`xxx_id`** |
| **3NF 拆传递** | 讲师职位、分类名不进业务表 → **讲师表 / 字典表** + 外键 |
| **1:N 拆子表** | 父 → 子 → 孙（如 课程→章节→小节）各一张表，子表存 **`{父}_id`** |
| **多对多 / 选课** | 用户 ↔ 课程 → **中间表**（如 `user_course`：谁选了哪门课） |
| **聚合单独存** | 多用户对同一对象打分 → **评价表**（每人一行），综合分再 **汇总/统计** |
| **相似实体合并** | 用户与讲师字段很像 → **user 表 + 角色/是否讲师**，业务表只关联 `user_id` |

**常见拆法（对照 3NF）：**

- **主表**：只留本实体属性 + 外键 id（如课程表：`title`、`category_id`、`teacher_id`）  
- **字典**：分类名、难度名在字典表维护，不在主表重复  
- **评价 / 问答 / 笔记**：独立表；业务主键常用 **用户 + 关联对象 + 标题** 等组合保证唯一  
- **评分维度**：实用性、易懂度等多列放 **评价表**，不要塞进课程主表一行  

**层级 1:N 示例：**

```
course ──1:N──> chapter ──1:N──> section
   ↑                  ↑
 course_id         chapter_id（在子表）
```

> 补：逻辑建模完成 ≈ 知道有哪些表、各存什么、谁 FK 谁；物理类型与命名在 2.6～2.9。

### 2.5 反范式 ★★★

逻辑建模按 **3NF** 拆完后，**查一次**可能要 **JOIN 多张表**；表越多，**高频查询**（如课程列表）越慢。

**反范式（反范式化）**：在**热点查询表**上故意**冗余字段 / 少 JOIN**，用**空间换时间**（可违反 2NF/3NF）。

**范式化带来的问题（查课示例）**

- 课程标题、方向在 **course**；章节在 **chapter**；小节在 **section**  
- 列表要展示「课名 + 章 + 小节 + 时长」→ 至少 **3 表 JOIN** + 关联条件  
- 用户每次打开列表都跑这条 SQL → 表多、JOIN 多 → 性能差  

**反范式怎么做**

| 思路 | 做法 |
|------|------|
| 子表冗余父信息 | **chapter** 表多加 `course_title`（来自 course） |
| 再往下冗余 | **section** 表多加 `course_title`、`chapter_title` |
| 效果 | 查列表/目录时 **少 JOIN**，SQL 更简单 |
| 代价 | 违反 2NF/3NF；改课名要 **同步更新** 子表冗余列 |

**课内取舍（3-19 总结）**

- **只动**访问频繁的 **chapter / section**；**course 主表、字典表、用户/评价/选课表** 一般不动  
- **流程**：先 **3NF 逻辑建模** → 看慢查询 → **有针对性**反范式，**有度**  
- **适用**：读多写少（列表、详情）；**不适用**核心字段频繁改写的 OLTP 主表  

> 补：反范式 ≠ 否定范式；是性能优化手段。更新冗余列要么应用层同步，要么定时任务/触发器（了解即可）。

### 2.5 练习 ★★★

#### 口述题

1. 范式拆太细，查询上会出现什么问题？  
2. 反范式是什么？牺牲什么换什么？  
3. 课内对 chapter/section 反范式的典型做法？  
4. 哪些表通常**不**反范式？  
5. 设计顺序：先范式还是先反范式？  

#### 答案

1. **多表 JOIN** 多，高频查询变慢。  
2. 热点表**冗余字段**减 JOIN；牺牲**范式/一致性维护**，换**查询性能**。  
3. 子表冗余父表标题（如 section 存 `course_title`、`chapter_title`）。  
4. **course 主表、字典表、用户/评价/选课** 等核心或低频 JOIN 表。  
5. 先 **3NF**，慢查询再**按需**反范式。  

#### 判断练习

「订单明细表冗余存 `product_name`，避免每次 JOIN 商品表」——算不算反范式？改商品名时要注意什么？

#### 判断练习答案

- **算**反范式（冗余换少 JOIN）。  
- 改商品名时要 **同步更新** 订单明细里的 `product_name`，否则历史展示不一致。  

### 2.6 存储引擎 ★★★★★

**物理设计第一步：** 每张表选**存储引擎** —— 决定数据**怎么落盘**、**怎么锁**、**支不支持事务**。

**常用引擎对比**

| 引擎 | 事务 | 锁 | 存储方式 | 适用 |
|------|------|-----|----------|------|
| **InnoDB** | ✅ ACID | **行锁** + MVCC | **聚簇索引**（按主键顺序存） | **业务 OLTP 默认** |
| MyISAM | ❌ | **表锁** | **堆表**（无固定顺序、无聚簇索引） | 老项目/只读归档，**新业务不用** |
| Memory | ❌ | 表锁 | 内存 | MySQL 内部**临时中间结果**；重启丢 |
| Archive | ❌ | 行锁 | 压缩、只增不改 | **日志 / 流水**（只 INSERT+SELECT） |
| CSV | ❌ | 表锁 | 类 CSV 文件 | **跨系统数据交换**，非核心业务 |
| Blackhole | ❌ | — | 写入即丢弃 | 复制/审计等特殊场景 |

- **MySQL 5.5+ 默认 InnoDB**；无特殊需求，**核心业务表全用 InnoDB**。  
- MyISAM：二级索引叶子指向**物理地址**，小范围查有时少一次回表；但读写都**锁整表**，高并发易阻塞。  
- Memory：IO 快但**易失**；一般不由业务主动建，多为优化器临时表。  

**InnoDB 三大特点**

1. **事务 ACID** — 转账、扣库存等必须用它。  
   - **禁止**同一事务里混 **InnoDB 表 + MyISAM/CSV 等非事务表** → 回滚时非事务表**改不回去**，破坏一致性。  

2. **聚簇索引（主键即数据组织方式）**  
   - 数据按**主键顺序**逻辑存储；**二级索引**叶子存的是**主键值**，再回表找行。  
   - 主键**越短、越有序**越好；主键乱序插入 → 页分裂、数据迁移 → **IO 损耗**。  
   - 实践：**自增 `id` 作数据库主键**；业务唯一键（如课程编号）建 **UNIQUE**，不必强当主键。  

3. **行锁 + MVCC** — 只锁涉及行，读写并发高；另支持**自适应哈希索引**（引擎自动、等值查加速，了解即可）。  

**版本能力（知道即可）**

- **5.6+**：InnoDB 支持**全文索引**（以前只能 MyISAM）。  
- **5.7+**：InnoDB 支持**空间索引**。  
- 因此现代 MySQL **不必**为全文/空间单独选 MyISAM。  

**怎么确认**

```sql
SHOW TABLE STATUS LIKE '表名';   -- Engine 列
-- 建表时
CREATE TABLE ... ENGINE=InnoDB;
```

> 补：本仓库 Flyway 脚本默认即 InnoDB（`ENGINE=InnoDB`）。

### 2.6 练习 ★★★★★

#### 口述题

1. 存储引擎解决什么问题？  
2. 业务 OLTP 表为什么默认 InnoDB？  
3. InnoDB 和 MyISAM 在事务、锁、存储上各怎样？  
4. 什么是聚簇索引？主键选型要注意什么？  
5. 同一事务里混用 InnoDB 和 MyISAM 会怎样？  

#### 答案

1. 决定物理存储、索引组织、锁粒度、是否支持事务。  
2. 要 **ACID**、**行锁**、高并发读写；5.5+ 默认引擎。  
3. InnoDB：有事务、行锁、聚簇索引；MyISAM：无事务、表锁、堆表。  
4. 数据按主键顺序存；主键即聚簇索引。**短且有序**（常用自增 id）；二级索引回表经主键。  
5. 非事务表修改**无法随事务回滚**，破坏原子性与一致性。  

#### 选型练习

日志表「只追加、从不 UPDATE/DELETE 历史行」——更倾向 **Archive** 还是 **InnoDB**？为什么？

#### 选型练习答案

- 倾向 **Archive**（只 INSERT+SELECT、压缩省空间）。  
- 若还要事务、频繁按条件查最新日志，仍用 **InnoDB**。  

### 2.7 字段类型 ★★★★★

**物理设计第二步：** 为每列选**合适类型**（范围、精度、空间、是否时区）。

**整数（够用即可，从小到大）**

| 类型 | 字节 | 有符号约范围 | 无符号约范围 |
|------|------|--------------|--------------|
| TINYINT | 1 | ±127 | 0～255 |
| SMALLINT | 2 | ±3.2万 | 0～6.5万 |
| MEDIUMINT | 3 | ±838万 | 0～1677万 |
| INT | 4 | ±21亿 | 0～42亿 |
| BIGINT | 8 | 更大 | 更大 |

- 有符号范围约 **−2^(8n−1) ～ 2^(8n−1)−1**（n = 字节数×8）  
- **UNSIGNED**：不存负数，**正数范围约翻倍**（如 TINYINT 0～255）  
- **`INT(11)` 的 11**：**显示宽度**，**不改变**存储字节与取值范围；想省空间应换 **TINYINT** 等小类型，不是写 `INT(2)`  
- 状态码 / 布尔：`TINYINT`；主键 / 外键常用 **BIGINT**（见 **2.8**）

**小数（实数）**

| 类型 | 特点 | 适用 |
|------|------|------|
| FLOAT / DOUBLE | **非精确**（4 / 8 字节） | 科学计算、可容忍误差 |
| **DECIMAL(M,D)** | **精确** | **金额、汇率、对账** |

- `11.11 + 11.11` 用 DOUBLE 可能 ≠ `22.22`（尾数多出一截）；**金额禁止 FLOAT/DOUBLE**  
- DECIMAL 存储：约 **每 4 字节存 9 位数字** + 小数点 1 字节；**5.0+ 最多 65 位**  
- 也可用 DECIMAL 存**超大整数**（比 BIGINT 还大时）

**日期时间**

| 类型 | 要点 |
|------|------|
| DATE | 只要日期；3 字节；约 1000-01-01～9999-12-31 |
| TIME | 时段；可 **>24h**（表示时长，如两日期间隔小时数）；3～6 字节（看小数秒位数） |
| **DATETIME** | 日期+时间；**不涉及时区**；5～8 字节；范围大 |
| **TIMESTAMP** | **按会话时区**显示；约 **1970～2038**；改 `time_zone` 同值显示会变 |
| YEAR | 年份；1 字节；1901～2155，比 SMALLINT/字符串更省 |

- 创建 / 更新时间：`DATETIME(3)` 或 `TIMESTAMP`；自动更新加 `ON UPDATE CURRENT_TIMESTAMP`  
- **跨时区、2038 后** → 优先 **DATETIME**；只在范围内且要时区语义时用 TIMESTAMP  

**字符串**

| 类型 | 要点 |
|------|------|
| **CHAR(n)** | **定长**（按**字符**宽度分配，utf8mb4 下一汉字最多 4 字节）；适合长度固定的码 |
| **VARCHAR(n)** | **变长**（按**字符**宽度定义，只占实际长度）；**最常用** |
| TEXT 系列 | 上限按**字节**：TINY(255B) / TEXT(64K) / MEDIUM(16M) / LONG(4G) |
| ENUM | 固定枚举（最多 65535 个值）；**改值要 ALTER**（慎用，见 **2.8**） |

- **utf8mb4**：一字符最多 4 字节；同表所有 **VARCHAR 宽度×字符集字节数** 之和 ≤ **65535 字节**  
- CHAR 即使只存 1 个字符也占满 n 个字符的空间；短且变长 → **VARCHAR**  

### 2.7 练习 ★★★★★

#### 口述题

1. 只存 0～255 的状态码，用 TINYINT 还是 INT(2)？为什么？  
2. 金额字段为什么用 DECIMAL 不用 DOUBLE？  
3. TIME 为什么可以大于 24 小时？  
4. DATETIME 和 TIMESTAMP 在时区、范围上各差在哪？  
5. CHAR(10) 和 VARCHAR(10) 在存储上差在哪？  

#### 答案

1. **TINYINT UNSIGNED**（或 TINYINT）；`INT(2)` 仍占 4 字节，范围不变。  
2. DOUBLE **非精确**，加减可能丢精度；对账必须 **DECIMAL**。  
3. TIME 可表示**时长/区间小时数**，不限于「一天内时刻」。  
4. DATETIME 不转换时区、范围大；TIMESTAMP 按时区显示、到 2038。  
5. CHAR **定长**占满 10 字符空间；VARCHAR **变长**只占实际内容。  

#### SQL 练习

```sql
-- 近似 vs 精确（3-26 演示）
CREATE TABLE t_num (d DOUBLE, m DECIMAL(10,2));
INSERT INTO t_num VALUES (11.11, 11.11), (11.11, 11.11);
SELECT d, d+d, m, m+m FROM t_num;

-- TIMESTAMP 随时区变化（3-28 演示）
CREATE TABLE t_ts (id INT PRIMARY KEY, ts_col TIMESTAMP);
SET time_zone = '+08:00';
INSERT INTO t_ts VALUES (1, NOW());
SET time_zone = '+00:00';
SELECT ts_col FROM t_ts WHERE id = 1;
```

### 2.8 字段选型 ★★★★

在 **2.7 类型清单**之上，按 **InnoDB + 业务**定列（与 **2.6 聚簇索引**配合）。

**一、按 InnoDB 优化主键与关联**

| 做法 | 原因 |
|------|------|
| 每表加 **自增 `id` 作数据库主键** | 聚簇索引短、有序插入，新行落在末尾，少页分裂 |
| 业务唯一列（标题、昵称、订单号）→ **UNIQUE**，不当 PK | 业务键常为字符串、乱序，不适合聚簇 |
| 表间关联用 **`xxx_id` 整型**，不用业务名关联 | 整型比字符串小、JOIN 更快 |
| 字典/讲师等 → 存 **id**，展示名靠 JOIN | 改一次主表，关联查询即一致 |

- **利**：一致性好、索引更瘦。  
- **弊**：列表要展示名时多一次 JOIN（或按需反范式，见 **2.5**）。  
- 课内取舍：核心业务优先 **id + JOIN**，少冗余名字。

**二、选类型的两条原则**

1. **优先：满足需求的最小类型**  
   - 非负且够用 → `UNSIGNED`（可能 INT 就能顶 BIGINT）  
   - **IPv4**：`INT UNSIGNED` + `INET_ATON` / `INET_NTOA`（4 字节 vs 字符串约 15 字节）；IPv6 → `VARBINARY(16)`  

2. **尽量少用 TEXT；慎用 ENUM**  
   - 备注/说明多数 **VARCHAR 够用**；TEXT 太大、排序易落**磁盘临时表**、读可能二次查找  
   - 必须用 TEXT → 可拆**扩展表**；查询**不要 `SELECT *`**；只能**前缀索引**、**不能默认值**  
   - **ENUM**：内部存整数，改枚举值要 **ALTER**（元数据锁，业务风险）→ 值常变用 **TINYINT + 字典表**  
   - **金额 / 价格 / 成本**：**DECIMAL**，禁止 FLOAT/DOUBLE  

> 补：时长汇总用「分钟整数」或应用层相加，别误用单个 TIME 硬扛总时长。

1. 为什么 InnoDB 表推荐自增 id 作主键，业务号放哪？

### 2.9 命名规范 ★★★

**物理设计最后一步：** 库、表、列命名 —— **见名知意、团队统一**。

**硬性约定**

| 规则 | 说明 |
|------|------|
| **禁用中文** | 库/表/列名一律不用中文 |
| **小写 + 下划线** | `order_item`；Linux 下库表名**大小写敏感**（对应文件名） |
| **禁止保留字** | 如 `order`、`group`、`index`、`desc`、`add`…（与关键字冲突易解析失败） |
| **见名知意** | 不用 `t1`；建议长度 ≤ **32**（非硬上限，过长不便用、占开销） |
| **多库可加前缀** | 表名带库/项目前缀（如 `imc_course`），一眼知归属 |

**临时表 / 备份表**

| 用途 | 约定 |
|------|------|
| 导入、统计中间结果 | **`tmp_` 前缀 + 日期后缀**（便于识别与清理） |
| 改表前库内备份（小表） | **`bak_` 前缀 + 日期后缀**；大表优先导出文件 |

**列名统一**

- **同义同名同类型**：全库统一 `user_id`，不混用 `uid` / `userId`（JOIN 与索引更好对齐）  
- **主键**：`id` 或 `{实体}_id`（团队统一一种即可）  
- **外键**：`{被引用实体}_id`  
- 时间 `created_at` / `updated_at`；计数 `xxx_cnt`；布尔 `is_xxx`  

> 补：命名无绝对标准，**团队约定一致**比「哪种英文更漂亮」更重要。

## 第3章 SQL

**本章路线：** 3.1 语句分类 → 3.2 DCL → 3.3 DDL·CREATE → 后续 ALTER/DROP、DML、TCL（边学边补）。

### 3.1 SQL 语句分类 ★★★★★

**SQL**（Structured Query Language）：**结构化查询语言**，专门用来操作**关系型数据库**里的数据。

- 是一种**描述性 / 面向语义**的语言：说清「从哪张表、什么条件、要什么」，就能写出语句；学起来通常比 Java/PHP 等通用语言门槛低  
- 主要能力：**增删改查**；也用于 Hive 等（用 SQL 查大数据），本笔记以 **MySQL** 为主  
- 日常开发：**DML 最多**；建表改表用 **DDL**；权限用 **DCL**；多步要原子性时用 **TCL**  

**四大类（必记）：**

| 分类 | 英文 | 管什么 | 代表语句 |
|------|------|--------|----------|
| **DCL** | Data Control Language | **访问控制**：用户、权限 | `CREATE USER`、`GRANT`、`REVOKE` |
| **DDL** | Data Definition Language | **库表结构**（定义对象） | `CREATE`、`ALTER`、`DROP`、`TRUNCATE`、`RENAME` |
| **DML** | Data Manipulation Language | **表里的数据**（增删改查） | `SELECT`、`INSERT`、`UPDATE`、`DELETE` |
| **TCL** | Transaction Control Language | **事务**开启/提交/回滚 | `START TRANSACTION`、`COMMIT`、`ROLLBACK` |

- **DCL**：建账号、授权、收权 —— 生产不要长期用 root 跑业务  
- **DDL**：改结构；`CREATE DATABASE` / `CREATE TABLE` 把第 2 章设计落地  
- **DML**：平时用得最多（查列表、下单写库）  
- **TCL**：转账、扣库存等「要么全成要么全撤」；课内事务细节在后面并发章再展开  

> 补：部分资料把 `SELECT` 单列为 DQL；本课并入 **DML**，知道即可。

### 3.1 练习 ★★★★★

#### 口述题

1. SQL 是什么？为什么说它是描述性语言？  
2. DCL / DDL / DML / TCL 各管什么？各举一条语句。  
3. 建表、改列类型属于哪类？查订单列表属于哪类？  
4. 提交和回滚属于哪类？什么时候要用？  
5. 后端日常写库，哪两类 SQL 接触最多？  

#### 答案

1. 结构化查询语言；按语义描述「查/改什么」，不是通用业务编程语言。  
2. DCL 权限 — `GRANT`；DDL 结构 — `CREATE TABLE`；DML 数据 — `SELECT`/`INSERT`；TCL 事务 — `COMMIT`/`ROLLBACK`。  
3. DDL；DML（SELECT）。  
4. TCL；多步写操作要原子性时（如扣款+记账）。  
5. **DML** 最多，其次 **DDL**（迁移/建表）。  

#### 归类练习

判断语句类型：`GRANT SELECT ON db.* TO u@'%'` · `ALTER TABLE t ADD col INT` · `DELETE FROM t WHERE id=1` · `ROLLBACK`

#### 归类答案

DCL · DDL · DML · TCL  

### 3.2 DCL · 用户与授权 ★★★★

生产环境**不要用 root 跑业务**。程序连库前先做三件事：**建账号 → 授权 → 多余权限收回**（均为 **DCL**）。

**三条核心语句**

| 语句 | 作用 |
|------|------|
| `CREATE USER` | 建账号 + 密码（可限主机、资源） |
| `GRANT` | 授予权限 |
| `REVOKE` | 收回权限 |

**用户身份 = `用户名@主机`**

- 主机可用 IP、网段（`192.168.1.%`）或 `%`（任意主机，**极不安全，慎用**）  
- `u@'192.168.1.%'` 与 `u@'192.168.2.%'` 是**两个不同账号**  

```sql
-- 建账号（8.0 默认认证插件多为 caching_sha2_password）
CREATE USER 'app_user'@'192.168.1.%'
  IDENTIFIED BY '强密码';

-- 可选：限制同时连接数等
CREATE USER 'app_user'@'192.168.1.%'
  IDENTIFIED BY '强密码'
  WITH MAX_USER_CONNECTIONS 10;
```

**常用业务权限（程序侧）**

| 权限 | 用途 |
|------|------|
| `SELECT` / `INSERT` / `UPDATE` / `DELETE` | 增删改查 |
| `EXECUTE` | 调存储过程/函数 |

```sql
-- 库级：该库下所有表（含之后新建的表）
GRANT SELECT, INSERT, UPDATE, DELETE
  ON app_db.* TO 'app_user'@'192.168.1.%';

-- 表级
GRANT SELECT ON mysql.user TO 'app_user'@'192.168.1.%';

-- 列级（隐藏敏感列时用）
GRANT SELECT (user, host) ON mysql.user TO 'app_user'@'192.168.1.%';

-- 收回多余写权限（只读账号）
REVOKE INSERT, UPDATE, DELETE
  ON app_db.* FROM 'app_user'@'192.168.1.%';

-- 查看当前版本支持的权限列表
SHOW PRIVILEGES;
FLUSH PRIVILEGES;  -- 改权限表后有时需刷新（了解即可）
```

**易错点（必记）**

1. **MySQL 8.0+**：`GRANT` **不会**自动建用户 → 必须先 `CREATE USER`，否则报错（如 1410）  
2. 执行 `GRANT` 的账号自身需有 **`GRANT OPTION`**，且**只能授予自己已有的权限**  
3. 未建库表前也可先建业务账号；库建好后再 `GRANT … ON 库.*`  
4. 只读应用不要给 `INSERT/UPDATE/DELETE`；系统库 `mysql.*` 勿给普通业务写权限  

> 补：`HELP CREATE USER;` / `HELP GRANT;` 可在客户端看完整语法。角色（ROLE）可批量管权限，了解即可。

### 3.2 练习 ★★★★

#### 口述题

1. DCL 三条常用语句各做什么？  
2. 为什么生产不用 root 跑业务程序？  
3. `user@'192.168.1.%'` 和 `user@'%'` 差在哪？  
4. MySQL 8.0 上只写 `GRANT`、不先 `CREATE USER` 会怎样？  
5. 只读报表账号该怎么授、怎么收？  

#### 答案

1. `CREATE USER` 建号；`GRANT` 授权；`REVOKE` 收权。  
2. root 权限过大，泄露/误操作风险极高。  
3. 前者限网段；后者任意主机，面过大。  
4. 报错：8.0 起 GRANT 不再自动建用户。  
5. 只 `GRANT SELECT`；若误授写权限用 `REVOKE INSERT,UPDATE, DELETE`。

### 3.3 DDL · CREATE ★★★★★

**DDL**（Data Definition Language）：定义库里的**对象**（库、表、索引、视图等）。本课先掌握 **CREATE**：建库、建表。

**常用 DDL 一览（认门类）**

| 对象 | 建 | 改 | 删 / 其它 |
|------|----|----|-----------|
| 库 | `CREATE DATABASE` | `ALTER DATABASE`（只能改字符集/排序规则等，**不能改库名**） | `DROP DATABASE`（连同库内对象与数据） |
| 表 | `CREATE TABLE` | `ALTER TABLE`（改结构；改 ENUM 等可能影响已有数据） | `DROP TABLE`；`TRUNCATE`；`RENAME TABLE` |
| 索引 | `CREATE INDEX` | — | `DROP INDEX`（不删表数据，可能改执行计划） |
| 视图 | `CREATE VIEW` | `ALTER VIEW` | `DROP VIEW` |

- **TRUNCATE**：效果类似「删表再按同结构建表」→ 属 **DDL**；清空数据、保留结构；**一般不记可回滚的行级删除日志**，勿当普通 DELETE 用。  
- **RENAME TABLE**：改名；也可在同实例**跨库移动表**；不改表内数据。  
- 索引：**不是越多越好**；多余索引拖慢写入、干扰优化器（索引细节后置）。

**建库**

```sql
CREATE DATABASE app_db
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

USE app_db;   -- 后续操作切到该库
```

- 库名：见名知意、小写下划线、避保留字（见 **2.9**）  
- 未指定字符集/排序规则 → 用**服务器默认**；业务库建议显式 **utf8mb4**  
- MySQL **不支持**常用的 `RENAME DATABASE`；库名错了只能新建再迁数据  
- `DROP DATABASE`：删库 + 库内全部对象与数据，只能靠**备份**恢复 → 确认无用且已备份再执行  

**建表（基本骨架）**

```sql
CREATE TABLE user (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  username    VARCHAR(64)     NOT NULL COMMENT '登录名',
  status      TINYINT         NOT NULL DEFAULT 1 COMMENT '状态',
  created_at  DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_username (username)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COMMENT='用户表';
```

| 部分 | 写什么 |
|------|--------|
| 表名 | `CREATE TABLE 表名`；可选 `TEMPORARY` → **临时表** |
| 列定义 | 名 + 类型 + 空/默认/自增/注释；也可在列上标主键/唯一 |
| 表级约束 | `PRIMARY KEY`、`UNIQUE KEY` 等 |
| 表选项 | `ENGINE`、字符集/排序规则、`COMMENT` |

**列上常用约束**

| 关键字 | 作用 |
|--------|------|
| `NOT NULL` | 不允许空 |
| `DEFAULT` | 默认值 |
| `AUTO_INCREMENT` | 自增（通常配主键） |
| `COMMENT` | 列/表备注，方便维护数据字典 |

**临时表：** `CREATE TEMPORARY TABLE …` — **仅当前会话**可见，断开即删；中间结果可用，不做业务持久表。

**表级字符集：** 未指定则继承**库**的默认；可与库不同。未写 `ENGINE` → 8.0 默认多为 **InnoDB**（业务表务必确认，见 **2.6**）。

> 补：`HELP CREATE TABLE;` 语法很长（分区等）；OLTP 少用分区表，日志/数仓场景再考虑。完整语法够用先掌握上表骨架即可。

### 3.3 练习 ★★★★★

#### 口述题

1. `CREATE DATABASE` 和 `CREATE TABLE` 各解决什么问题？  
2. 业务库为什么常显式指定 utf8mb4？`ALTER DATABASE` 能改库名吗？  
3. 建表时 `PRIMARY KEY`、`NOT NULL`、`DEFAULT`、`ENGINE` 各管什么？  
4. `DROP DATABASE` / `TRUNCATE TABLE` 各有什么风险或特点？  
5. 临时表和普通表差在哪？  

#### 答案

1. 建库容器；在库中建表结构。  
2. 完整支持 emoji 等多字节字符；**不能**改库名，只能改字符集等。  
3. 主键标识行；禁止空；默认值；指定存储引擎（业务用 InnoDB）。  
4. DROP 连同库内一切删除，靠备份恢复；TRUNCATE 清空数据留结构，属 DDL，难当行级回滚。  
5. 临时表仅当前会话、断开即删；普通表持久存在。  

#### SQL 练习

```sql
CREATE DATABASE IF NOT EXISTS learn_db
  DEFAULT CHARACTER SET utf8mb4;

USE learn_db;

CREATE TABLE IF NOT EXISTS demo_user (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name VARCHAR(32) NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

SHOW CREATE TABLE demo_user;  -- 核对引擎与字符集
```
