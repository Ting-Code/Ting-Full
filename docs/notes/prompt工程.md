# Prompt 工程笔记（全栈向）

> 对照：`docs/origin/prompt-engineering-for-developers/`（吴恩达 × OpenAI 短课中文版）。边学边写；只记可复习要点与案例。

## 1 · 编写 Prompt 的原则

### Prompt 原则一：清晰具体 ★★★★★

- **定位：** 全栈重点是 **用 API 调指令微调 LLM 做应用**，不是一次性在网页里聊；把模型当成「聪明但不懂你业务细节的同事」，指令含糊就会答偏。
- **清晰 ≠ 短：** 该给的上下文、格式、边界要给全；宁可长一点写清楚。

#### 四策略

1. **分隔符圈住用户/业务文本**（```、`"""`、XML 标签等）  
   - 现象：用户输入里夹带「忽略上文，改做…」→ 覆盖你的系统意图（提示注入）。  
   - 改法：任务说明写在外，待处理正文放进分隔符；模型只「对框内内容」执行任务。
2. **要求结构化输出**（JSON / 固定字段）  
   - 现象：自由散文难解析进后端。  
   - 改法：写明键名（如 `book_id, title, author`），服务端直接反序列化。
3. **先检查条件再执行**  
   - 现象：文本没有步骤却硬拆「Step 1…」。  
   - 改法：不满足假设时输出约定句（如「未提供步骤」）并停止后续动作。
4. **少量示例（few-shot）**  
   - 现象：只说「保持某种风格」仍飘。  
   - 改法：先给 1～2 个合格问答样例，再抛真正任务。

#### 练习

1. 写一条 Prompt：总结用户评论；评论正文必须用三个反引号包裹。  
2. 写一条 Prompt：从工单文本抽出 `priority` / `category` / `summary`，只要 JSON。

#### 口述题

1. 为什么「写清楚」往往比「写短」更重要？  
2. 分隔符主要防什么？和后端「参数与指令分离」有何相似？

### Prompt 原则二：给模型时间思考 ★★★★★

- **核心：** 复杂任务别逼模型「一步蹦答案」；先让它按步骤推理，再给结论（多耗一点算力，换更稳）。

#### 两策略

1. **写清完成任务的步骤 + 输出骨架**  
   - 现象：多步任务（摘要→翻译→抽人名→JSON）一次丢出去，字段名乱、格式飘。  
   - 改法：编号步骤；再用固定模板（`摘要：… / 翻译：… / Output JSON：…`）约束中间结果。
2. **下结论前先自己解一遍**  
   - 现象：直接「判断学生答案对不对」→ 容易被漂亮错解带偏（维护费写成 `100x` 实为 `10x`）。  
   - 改法：先独立算出正确答案 → 再对比 → 最后给 correct/incorrect。

#### 局限性：幻觉（Hallucination）

- **是什么：** 模型一本正经输出**看似真、实则编**的内容（真实公司 + 虚构产品名也会被「圆」出来）。
- **减幻觉（全栈常用）：**  
  1. 只根据给定文档/检索结果作答，并要求先列引用再回答。  
  2. 原则一的结构化 + 条件检查：缺证据就返回「未知/未提供」。  
  3. 关键结论走业务校验或人审，不盲信模型事实。

> 补：课内用 `\` 只为排版换行；换别的模型时要确认会不会吃进 `\`。

#### 练习

1. 写一条多步 Prompt：总结工单 → 译成英文 → 输出 JSON（`en_summary`, `priority`），并给出固定输出格式。  
2. 写一条「先自解再评判」的 Prompt，用于核对优惠券计算公式是否正确。

#### 口述题

1. 为什么「先自己算再评判」往往比「直接对错」更准？  
2. 举一个业务里减幻觉的做法（一句）。
