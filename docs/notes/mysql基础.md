# MySQL 基础

## 第1章 选型

**本章路线：** 1.1～1.3 SQL/NoSQL 与适用场景 → 1.4 定 MySQL → 1.5 练习。

### 1.1 SQL vs NoSQL ★★★

|     | **SQL（关系型）**         | **NoSQL（非关系型）**              |
| --- | -------------------- | ---------------------------- |
| 含义  | 用 **SQL** 操作         | **Not Only SQL**（不是「不要 SQL」） |
| 形态  | 库 → 表 → 行/列          | 文档 / 键值等，模型多样                |
| 常见  | **MySQL**、PostgreSQL | MongoDB、**Redis**            |
| 访问  | 标准 **SQL**           | 各自 API，不统一 SQL               |

- 强关系、要事务 → 业务核心用 **MySQL**。  
- 缓存 / Token → **Redis**，与 MySQL **分工**，不是替换。

### 1.2 关系型：特点与适用 ★★★

| 特点       | 一句话                       |
| -------- | ------------------------- |
| **结构化**  | 存之前先定表结构；标准二维表（行/列、同列同类型） |
| **ACID** | 事务要么全成功要么全回滚，保证数据可靠       |
| **SQL**  | 查询、合并、聚合、多表关联             |

**ACID 四字（先记名）：** 原子性、一致性、隔离性、持久性。转账/扣库存不能执行一半。

部分新版本支持 **JSON 列**存半结构化数据，但主体仍是表结构思维。

**什么时候适合：** 实体之间有关系，且要**严格保证数据正确**。

| 关系例子           | 说明                  |
| -------------- | ------------------- |
| 订单 ↔ 订单明细 ↔ 商品 | 一件商品可进多笔订单，一笔订单多行明细 |
| 用户 ↔ 笔记        | 一人多篇笔记，一篇笔记只属于一人    |

要做统计、报表、复杂查询 → **SQL + 关系型**更合适。NoSQL 对事务/一致性支持通常较弱。

### 1.3 非关系型：特点与适用 ★★★

| 特点          | 一句话                       |
| ----------- | ------------------------- |
| **灵活模型**    | 不必先定死表结构；同集合里各行字段可不同      |
| **弱化 ACID** | 往往换更高读写吞吐；难做银行级事务         |
| **非统一 SQL** | Mongo 用文档 API；Redis 用键值命令 |

**典型场景：**

- **日志 / 埋点**：写入量大，偶尔丢几条可接受  
- **结构多变**：商品属性各不同，适合文档库  
- **高并发轨迹**：行为流等，关系型扛不住时  
- **缓存 / 会话**：热点数据 → **Redis**  
- **排行榜 / 计数**：Redis 原子增减等

注意：占空间通常比关系型大；**不能替代**订单、支付等要强一致的核心库。

### 1.4 选型步骤与定 MySQL ★★★

关系型里还要再选具体产品，可按下面 **五步** 筛：

| 步骤    | 看什么                          |
| ----- | ---------------------------- |
| 生态与普及 | 用的人多不多？资料、招人容不容易             |
| 成熟度   | 用得久、够稳定，才敢上生产                |
| 扩展性   | 数据量上来能否主从、分库分表（中间件先认名）       |
| 安全与稳定 | 加密、权限、备份恢复是否满足企业要求           |
| 成本与部署 | 授权费、是否支持你的 OS（Linux/Windows） |

原则：**合适比喜欢更重要**。

**定 MySQL 的常见理由：**

- 开源免费，国内 Java 生态最好  
- 主从复制、读写分离；配合 MyCat / MHA 等可扩展（细节后学）  
- 权限可到库/表/行级；支持 Linux 与 Windows  
- 排行榜常年前三，招聘与社区资源多

Oracle / SQL Server 偏商业授权；中小项目预算有限时 → **MySQL**。

### 1.5 练习 ★★★

#### 口述题

1. NoSQL 全称含义？MySQL 和 Redis 怎么分工？  
2. 关系型三大特点？ACID 管什么？  
3. NoSQL 常见适用场景？为什么不替代订单库？  
4. 选型五步各看什么？为什么常选 MySQL？  
5. 订单和商品为什么适合关系型？  

#### 答案

1. **Not Only SQL**；MySQL 业务表/事务，Redis 缓存/KV。  
2. 结构化、ACID、SQL；事务可靠、不能半路烂尾。  
3. 日志/埋点、结构多变、高并发轨迹、缓存会话、排行榜计数；订单支付要强一致。  
4. 生态→成熟→扩展→安全→成本/OS；开源、Java 生态、可扩展。  
5. 多实体有关联，要 JOIN + 事务保证金额、库存不错。  

## 第2章 表设计

**本章路线：** 2.1 流程 → 2.2～2.5 逻辑（宽表 / 范式 / 建模 / 反范式）→ 2.6～2.9 物理（引擎 / 类型 / 选型 / 命名）。

### 2.1 表设计流程 ★★★★

**三步（建表前）：**

| 步骤 | 干什么 |
|------|--------|
| **业务分析** | 列实体、列属性、标关系（常见 **1:N**）；只清单，不写 SQL |
| **逻辑设计** | 宽表/范式、拆表；影响扩库与查询 |
| **物理设计** | 引擎、字段类型、命名（2.6～2.9） |

先逻辑后物理。落库：`CREATE DATABASE` / `CREATE TABLE`（第 3 章起学 SQL）。

### 2.1 练习 ★★★★

#### 口述题

1. 建表前三步各干什么？  
2. 「实体」和「属性」是什么？  
3. 常见实体关系？清单列完能否直接建表？  

#### 答案

1. 业务（存什么）→ 逻辑（怎么拆）→ 物理（类型与引擎）。  
2. 实体 = 业务对象；属性 = 描述它的字段。  
3. 常见 **1:N**；不能，还要定表结构与范式。  

### 2.2 宽表 ★★★★

- **宽表**：多实体挤一张表，同一信息**多行重复**  
- **三大异常**：**更新**（改一处要改多行）· **插入**（缺主数据插不进）· **删除**（删业务顺带丢字典）  
- **OLTP 宜拆表**（主数据单表 + 外键）；**报表**可读多写少、少 JOIN 时用宽表  

### 2.2 练习 ★★★★

#### 口述题

1. 宽表三大异常各是什么？  
2. 在线业务为什么少用宽表？  
3. 怎么从设计上规避宽表问题？  

#### 答案

1. 更新多行不一致；插入绑死插不进；删除连带丢主数据。  
2. OLTP 写入多，异常代价大。  
3. 拆表去冗余，字典/主数据独立表。  

### 2.3 三大范式 ★★★★★

口诀：**1NF 管原子，2NF 管完全依赖，3NF 管传递依赖**。逐级满足，不可跳级。

| 范式 | 要求 | 违规 → 改法 |
|------|------|-------------|
| **1NF** | 字段**不可再分** | 联系方式拼一格 → 拆成多列 |
| **2NF** | 非主键**完全依赖整个主键** | 复合主键表里塞只跟部分键有关的列 → 拆出去 |
| **3NF** | 非主键**只依赖主键**，不依赖别的非主键 | 订单表存「用户等级」（等级跟用户走）→ 拆用户表 |

- 业务 OLTP 表：目标至少 **3NF**  
- 报表层可适度反范式换查询速度  
- 通法：违规列 → 独立表 + 外键  

### 2.3 练习 ★★★★★

#### 口述题

1. 1NF / 2NF / 3NF 各管什么？  
2. 联系方式「手机/座机/邮箱」拼一列，违反哪条？  
3. 复合主键选课表里存「用户积分」（积分只跟用户有关），违反哪条？  
4. 订单表存「用户等级」（等级只跟用户有关），违反哪条？  
5. 业务表一般至少要几范式？  

#### 答案

1. 原子 / 完全依赖 / 无传递依赖。  
2. **1NF**。  
3. **2NF**。  
4. **3NF**。  
5. 至少 **3NF**（报表另说）。  

### 2.4 逻辑建模 ★★★★

范式定完后，把实体**落成表结构**（仍不写具体 SQL 类型）：

| 原则 | 做法 |
|------|------|
| **一实体一表** | 用户、订单、商品等各一张表 |
| **字典独立** | 分类、状态码 → 字典表，业务表只存 **外键 id** |
| **3NF 拆传递** | 职位不进业务表 → 独立表 + `xxx_id` |
| **聚合单独存** | 多用户对一对象打分 → **评价表**，再汇总 |
| **1:N 用外键** | 父表 id → 子表 `{父}_id` |

> 补：属性相近的实体可合并（如用户 + 角色），用外键关联业务。

### 2.4 练习 ★★★★

#### 口述题

1. 逻辑建模在流程里处于哪一步之后？  
2. 分类、状态为什么要字典表？  
3. 综合评分为什么不只放主表一列？  

#### 答案

1. 业务分析、范式分析之后。  
2. 避免冗余与增删改异常；业务表只存 `category_id` 等。  
3. 评分来自多用户，独立评价表才符合 3NF。  

### 2.5 反范式 ★★★

- **范式过细** → 查一次要 **多表 JOIN** → 表越多，高频查询越慢  
- **反范式**：在**热点查询表**上故意**冗余字段 / 减少 JOIN**，用空间换时间（可违反 2NF/3NF）  
- **适用**：读多写少的列表、详情；**不适用**核心业务频繁改写  
- **原则**：先 **3NF** 设计，再按慢查询**有针对性**反范式；**有度**  
- 常只动少数表，字典表、用户表等一般不动  

> 补：反范式后 `UPDATE` 要同步冗余列 — 只用在值得优化的查询上。

### 2.5 练习 ★★★

#### 口述题

1. 为什么要反范式？  
2. 反范式牺牲了什么？  
3. 业务表设计一般先范式还是先反范式？  

#### 答案

1. 减少 JOIN，提升高频查询性能。  
2. 冗余、可能违反范式、更新时要同步多列。  
3. 先 **3NF**，热点再按需反范式。  

### 2.6 存储引擎 ★★★★★

**物理设计第一步：** 选**存储引擎**（表数据怎么落盘、怎么锁、支不支持事务）。

| 引擎 | 要点 | 业务库 |
|------|------|--------|
| **InnoDB** | 事务 ACID、**行锁**、**聚簇索引**（按主键存数据） | **默认首选** |
| MyISAM | 表锁、无事务、堆存储 | 一般不用于业务 |
| Memory | 内存表，重启丢 | 临时中间结果 |
| Archive | 只插只查、压缩 | 日志类归档 |

**InnoDB 必记：**

- **事务 ACID**；同一事务里**不要混** InnoDB 与 MyISAM  
- **聚簇索引**：数据按主键顺序存（主键选型见 **2.8**）  
- **MVCC + 行锁**，适合高并发读写  
- **8.0+** 支持全文索引；业务表**默认全 InnoDB**  
- 确认引擎：建表 `ENGINE=InnoDB` 或 `SHOW TABLE STATUS`  

### 2.6 练习 ★★★★★

#### 口述题

1. 存储引擎解决什么问题？  
2. 业务 OLTP 表为什么默认 InnoDB？  
3. InnoDB 和 MyISAM 在锁粒度、事务上各怎样？  
4. 什么是聚簇索引？  
5. 同一事务里混用 InnoDB 和 MyISAM 会怎样？  

#### 答案

1. 决定数据物理存储、索引与锁、是否支持事务。  
2. 要事务、行锁、高并发读写。  
3. InnoDB 行锁 + 有事务；MyISAM 表锁 + 无事务。  
4. 数据按主键顺序存储；主键即聚簇索引。  
5. 无法保证整体原子性，事务语义被破坏。  

### 2.7 字段类型 ★★★★★

**物理设计第二步：** 为每列选**合适类型**（范围、精度、空间、是否时区）。

**整数（够用即可，从小到大）**

| 类型 | 字节 | 有符号约范围 | 无符号约范围 |
|------|------|--------------|--------------|
| TINYINT | 1 | ±127 | 0～255 |
| SMALLINT | 2 | ±3.2万 | 0～6.5万 |
| INT | 4 | ±21亿 | 0～42亿 |
| BIGINT | 8 | 更大 | 更大 |

- **UNSIGNED**：只存非负数时可用，正数范围约翻倍  
- **`INT(11)` 的 11**：显示宽度，**不改变**存储与范围  
- 状态码 / 布尔：`TINYINT`；主键 / 外键常用 **BIGINT**（见 **2.8**）

**小数**

| 类型 | 特点 | 适用 |
|------|------|------|
| FLOAT / DOUBLE | **近似**存储 | 科学计算、可容忍误差 |
| **DECIMAL(M,D)** | **精确** | **金额、汇率、对账** |

- `11.11 + 11.11` 用 DOUBLE 可能 ≠ `22.22`；**金额禁止 FLOAT/DOUBLE**

**日期时间**

| 类型 | 要点 |
|------|------|
| DATE | 只要日期 |
| TIME | 时段，可 >24h（表示时长） |
| **DATETIME** | 日期+时间；**不涉及时区**；范围大 |
| **TIMESTAMP** | **按会话时区**；约 1970～2038 |
| YEAR | 年份，1 字节 |

- 创建 / 更新时间：`DATETIME(3)` 或 `TIMESTAMP`；自动更新加 `ON UPDATE CURRENT_TIMESTAMP`  
- 跨时区、2038 后 → 优先 **DATETIME**

**字符串**

| 类型 | 要点 |
|------|------|
| **CHAR(n)** | 定长；适合长度固定的码 |
| **VARCHAR(n)** | 变长；**最常用** |
| TEXT 系列 | TINY(255B) / TEXT(64K) / MEDIUM(16M) / LONG(4G)；大段文本 |
| ENUM | 固定枚举；**改值要 ALTER**（慎用，见 **2.8**） |

- **utf8mb4**：一字符最多 4 字节；行总长约 65535 字节上限  

### 2.7 练习 ★★★★★

#### 口述题

1. TINYINT 和 BIGINT 各适合什么列？  
2. 金额字段为什么用 DECIMAL 不用 DOUBLE？  
3. DATETIME 和 TIMESTAMP 在时区、范围上各差在哪？  
4. CHAR 和 VARCHAR 怎么选？  
5. `INT(11)` 里的 11 表示什么？  

#### 答案

1. 状态/布尔 → TINYINT；主键/外键/大 id → BIGINT（见 **2.8**）。  
2. DOUBLE 近似存，加减可能丢精度；对账必须精确。  
3. DATETIME 不转换时区、范围大；TIMESTAMP 按时区显示、到 2038。  
4. 定长且短 → CHAR；长度变化 → VARCHAR。  
5. 显示宽度，与存储字节和取值范围无关。  

#### SQL 练习

```sql
-- 近似 vs 精确
CREATE TABLE t_num (d DOUBLE, m DECIMAL(10,2));
INSERT INTO t_num VALUES (11.11, 11.11), (11.11, 11.11);
SELECT d, d+d, m, m+m FROM t_num;

-- TIMESTAMP 随时区变化（需先建含 TIMESTAMP 列的表）
CREATE TABLE t_ts (id INT PRIMARY KEY, ts_col TIMESTAMP);
SET time_zone = '+08:00';
INSERT INTO t_ts VALUES (1, NOW());
SET time_zone = '+00:00';
SELECT ts_col FROM t_ts WHERE id = 1;
```

### 2.8 字段选型 ★★★★

在 **2.7 类型清单**之上，按 **InnoDB + 业务**定列（与 **2.6 聚簇索引**配合）。

**主键与关联**

- 代理 PK：**自增 BIGINT `id`**；**不用**长字符串业务号当 PK  
- 业务唯一码 → **UNIQUE**（非主键）  
- 表间关联 → **`xxx_id` 整型 FK**  
- 强一致展示名 → **id + JOIN**，慎多处冗余名字  
- 小范围计数列可用 **SMALLINT** 等；PK/FK 仍常用 BIGINT  

**类型与特殊列**

- 整数：范围定死且不大 → `SMALLINT UNSIGNED` 等  
- **IPv4**：`INT UNSIGNED` + `INET_ATON` / `INET_NTOA`；IPv6 → `VARBINARY(16)`  
- 短文本：**VARCHAR 够用就不用 TEXT**（索引、排序、临时表更友好）  
- **TEXT**：无默认、仅前缀索引 → 大字段可拆扩展表，避免 `SELECT *`  
- **ENUM**：值常变 → 改 **TINYINT + 字典表**  
- **金额**：**DECIMAL**；**总时长**：多段相加用分钟整数或应用层汇总，别误用单个 TIME  

### 2.8 练习 ★★★★

#### 口述题

1. 为什么 InnoDB 表推荐自增 id 作主键，业务号放哪？  
2. 冗余存昵称和存 `user_id` 各有什么问题？  
3. IP 为什么可以存 INT UNSIGNED？  
4. TEXT 相比 VARCHAR 在索引、默认值上有何限制？  
5. ENUM 什么时候不建议用？  

#### 答案

1. 聚簇索引短、顺序插入快；业务号建 UNIQUE 即可。  
2. 冗余易不一致、更新面大；id + JOIN 一致性好。  
3. IPv4 可映射为 32 位无符号整数，4 字节比字符串省。  
4. TEXT 通常不能默认值、不能整列索引（仅前缀），临时表/排序代价高。  
5. 枚举值经常增删改、需频繁 ALTER 时。  

#### 设计练习

为「用户—订单」列出：`id`、业务号、金额、状态、创建时间 各用什么类型/键。

#### 设计练习答案

| 列 | 用户表 | 订单表 |
|----|--------|--------|
| id | BIGINT PK AI | BIGINT PK AI |
| 业务号 | — | order_no VARCHAR UNIQUE |
| 金额 | — | amount DECIMAL(10,2) |
| 状态 | — | status TINYINT（或字典表 id） |
| 创建时间 | created_at DATETIME(3) | created_at DATETIME(3) |
| 关联 | — | user_id BIGINT（FK） |

### 2.9 命名规范 ★★★

**物理设计第三步：** 库、表、列 **见名知意、团队统一**。

**库 / 表**

- **小写 + 下划线**；Linux 下库表名**区分大小写**  
- **语义化**：`order_item`，不用 `t1`  
- **避开保留字**：`order`、`group`、`index`、`desc` 等  
- 长度建议 ≤ **32** 字符；多库可加**项目前缀**（如 `app_user`）  

**临时 / 备份表**

| 用途 | 约定 |
|------|------|
| 导入、统计中间结果 | **`tmp_`** 前缀或 **`_tmp`** 后缀 |
| 改表前备份 | **`bak_`** 前缀或 **`_bak`** 后缀 |

**列名统一**

- 同义**全库同名、同类型**：统一 `user_id`，不混用 `uid`  
- **主键** `id`；**外键** `{实体}_id`  
- 时间 `created_at` / `updated_at`；计数 `view_cnt`；布尔 `is_deleted`  

### 2.9 练习 ★★★

#### 口述题

1. 库表名为什么推荐小写 + 下划线？  
2. 临时表、备份表如何命名？  
3. 为什么列名要跨表统一？  
4. 外键列一般怎么命名？  
5. 使用 MySQL 保留字作表名会怎样？  

#### 答案

1. 跨平台一致；Linux 大小写敏感，小写少踩坑。  
2. `tmp_` / `_tmp`；`bak_` / `_bak`。  
3. JOIN、代码映射简单，减少写错列名。  
4. 被引用实体 + `_id`。  
5. 需反引号包裹，易与语法冲突。  

#### 改错练习

哪些不合规范：`Order`、`tmpData`、`group`、`uid`/`user_id` 混用、`courseTitle`？

#### 改错答案

- `Order` → `purchase_order`  
- `tmpData` → `tmp_import_data`  
- `group` → `user_group`  
- 混用 → 统一 `user_id`  
- `courseTitle` → `course_title`  

## 第3章 SQL

**本章路线：** 3.1 语句分类 → 后续 DDL / DML / TCL（边学边补）。

### 3.1 SQL 语句分类 ★★★★★

**SQL**（Structured Query Language）：**结构化查询语言**，用来操作**关系型数据库**里的数据。

- 不是 Java 那种通用编程语言，而是**围绕表**的声明式语言  
- 日常开发：**DML 最多**；建表改表用 **DDL**；权限用 **DCL**；多步要原子性时用 **TCL**  
- 也用于 Hive 等大数据查询，但本笔记以 **MySQL** 为主  

**四大类（必记）：**

| 分类 | 英文 | 管什么 | 代表语句 |
|------|------|--------|----------|
| **DCL** | Data Control Language | 用户、权限 | `CREATE USER`、`GRANT`、`REVOKE` |
| **DDL** | Data Definition Language | **库表结构**（定义对象） | `CREATE`、`ALTER`、`DROP`、`TRUNCATE`、`RENAME` |
| **DML** | Data Manipulation Language | **表里的数据**（增删改查） | `SELECT`、`INSERT`、`UPDATE`、`DELETE` |
| **TCL** | Transaction Control Language | **事务**提交/回滚 | `START TRANSACTION`、`COMMIT`、`ROLLBACK` |

- **DDL**：改结构；`CREATE DATABASE` / `CREATE TABLE` 把第 2 章设计落地  
- **DML**：`SELECT` 查、`INSERT`/`UPDATE`/`DELETE` 改数据 — **用得最多**  
- **TCL**：转账、扣库存等「要么全成要么全撤」时配合 DML  
- **DCL**：生产环境按最小权限建账号；本地练习常用 root，上线要换专用账号  

> 补：部分资料把 `SELECT` 单列为 DQL；本课并入 **DML**，知道即可。

### 3.1 练习 ★★★★★

#### 口述题

1. SQL 是什么？和 Java 的定位差在哪？  
2. DCL / DDL / DML / TCL 各管什么？各举一条语句。  
3. 建表、改列类型属于哪类？查订单列表属于哪类？  
4. 提交和回滚属于哪类？什么时候要用？  
5. 后端日常写库，哪两类 SQL 接触最多？  

#### 答案

1. 结构化查询语言；专门操作关系库，不是通用业务编程语言。  
2. DCL 权限 — `GRANT`；DDL 结构 — `CREATE TABLE`；DML 数据 — `SELECT`/`INSERT`；TCL 事务 — `COMMIT`/`ROLLBACK`。  
3. DDL；DML（SELECT）。  
4. TCL；多步写操作要原子性时（如扣款+记账）。  
5. **DML** 最多，其次 **DDL**（迁移/建表）。  

#### 归类练习

判断语句类型：`GRANT SELECT ON db.* TO u@'%'` · `ALTER TABLE t ADD col INT` · `DELETE FROM t WHERE id=1` · `ROLLBACK`

#### 归类答案

DCL · DDL · DML · TCL
